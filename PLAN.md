# Тесты для huEVO — план

Игра-каталог тестов в духе старого ВК: «Кто ты из Наруто?», «Какой ты смайлик?» и т.д. Плюс любой игрок может **создать свой тест**.

## 1. Что говорят доки (важное для дизайна)

- Игра = обычный веб-сайт на **нашем домене**, huEVO показывает его в `iframe` (16:9 / 4:3, на экранах <700px всегда 9:16 — **проектируем mobile-first, вертикально**).
- Нужен **свой backend** (хостинг + домен + HTTPS). Cloudflare Workers/Pages или VPS — оба подходят.
- Запуск: во фрейм приходят `hu_user_id, hu_username, hu_display_name, hu_avatar, hu_mode, hu_ts, hu_hash`. Сервер проверяет `hu_hash` (HMAC-SHA256, ключ = SHA256(client_secret), строка из отсортированных `hu_*` через `\n`), потом выдаёт **свой токен сессии**. Данные с клиента не доверенные.
- Sandbox: `allow-scripts allow-same-origin allow-forms allow-pointer-lock`. Нельзя: `window.open`, `alert/confirm/prompt`, буфер обмена, камера, `requestFullscreen`. → свои модалки, внешние ссылки только через `huevo.openLink`.
- 3rd-party cookie могут блокироваться → **токен в `localStorage` + заголовок `Authorization`**, не cookie.
- SDK: `huevo.init()`, `share()`, `openProfile(userId)`, `openLink(url)`, `fullscreen()`, события `pause/resume`.
- **`share()` без аргументов — шарит только ссылку на страницу игры**, глубокой ссылки на конкретный тест нет. Это главное ограничение вирусности (см. риски).
- Apps API (`users.get`, кошелёк, платежи) нам на старте **не нужен** — монетизацию пока не трогаем.
- Лимиты приложения: 5 тегов, название 2–64, описание ≤1000, URL ≤300. Статусы: черновик → модерация → публикация. Есть режим `test` (черновик, только владелец и тестеры).

## 2. Продуктовая идея

**Два типа тестов** (покрывают 95% того, что было в ВК):

1. **Тест-«кто ты»** (personality): N вопросов, у каждого ответа «веса» по результатам (персонажи). Побеждает результат с макс. суммой. Пример: Наруто, Саске, Сакура…
2. **Тест-викторина** (quiz): правильные/неправильные ответы, результат по диапазону баллов («0–3: новичок, 4–7: …»).

Технически это одна модель: ответ добавляет очки одному или нескольким результатам; в quiz правильный ответ даёт +1 к «баллам», итог — по диапазонам.

**Экраны:**
- **Главная**: вкладки «Популярные / Новые / Мои»; поиск и теги; карточки (обложка, название, автор, число прохождений, лайки).
- **Страница теста**: обложка, описание, автор (клик → `openProfile`), «Начать».
- **Прохождение**: один вопрос на экран, прогресс-бар, анимация, кнопка «назад».
- **Результат**: картинка + текст результата, % «таких же как ты» (доля прохождений с этим результатом), кнопки «Пройти ещё раз», «Поделиться» (`share()`), лайк, жалоба.
- **Конструктор**: шаги (1) название/обложка/теги → (2) результаты (название, описание, картинка) → (3) вопросы и ответы с распределением очков → (4) предпросмотр (пройти самому) → (5) публикация. Автосохранение черновика.
- **Мои тесты**: черновики, опубликованные, статистика (прохождения, распределение результатов), редактирование/удаление.
- **Админка/модерация** (отдельная страница под ключом): очередь жалоб, скрыть/удалить тест, бан автора.

## 3. Пользовательский контент = модерация (важно)

Игру проверяет huEVO, но контент игроков — наша ответственность.
- Лимиты: тестов на пользователя в день (напр. 5), вопросов ≤ 20, результатов ≤ 12, длина текстов.
- Обложки: **не грузим файлы на старте**, а даём выбор из готовых иллюстраций/эмодзи-градиентов (нет хранилища, нет NSFW-картинок). Загрузка картинок — этап 2 (с premod).
- Тест виден публично сразу после публикации (постмодерация) + кнопка «Пожаловаться»; N жалоб → автоскрытие до проверки. Стоп-слова на очевидное.
- Весь пользовательский текст рендерим **только как текст** (никакого `innerHTML`) — защита от XSS.
- Бан автора по `hu_user_id`.

## 4. Стек и архитектура

| Слой | Выбор | Почему |
|---|---|---|
| Frontend | **Vite + Preact (или Svelte)** + TypeScript, mobile-first CSS | лёгкий бандл, быстрая загрузка во фрейме |
| Backend | **Node.js + Hono/Fastify** (или Cloudflare Workers + D1) | проверка hash, REST API |
| БД | **SQLite/Postgres** (D1 если Workers) | пользователи, тесты, прохождения |
| Авторизация | `hu_hash` → наш JWT, хранится в `localStorage` | см. доки |
| Хостинг | один домен, фронт и API на одном origin (проще с iframe/CORS) | origin должен совпадать с URL в настройках игры, без редиректов |

**Схема БД:**
- `users(id = hu_user_id, username, display_name, avatar, banned, created_at)`
- `tests(id, author_id, type, title, description, cover, tags, status[draft|published|hidden], plays, likes, created_at)`
- `results(id, test_id, title, description, image, min_score, max_score)` — min/max только для quiz
- `questions(id, test_id, text, position)`
- `answers(id, question_id, text, correct bool)`
- `answer_scores(answer_id, result_id, points)` — веса для personality
- `plays(id, test_id, user_id, result_id, created_at)` — одна запись на прохождение
- `likes(user_id, test_id)`, `reports(id, test_id, user_id, reason, created_at)`

**API (все кроме /login требуют токен):**
`POST /login` · `GET /tests?sort=&tag=&q=` · `GET /tests/:id` · `POST /tests/:id/finish {answers[]}` (**подсчёт результата на сервере**) · `POST /tests` · `PUT /tests/:id` · `POST /tests/:id/publish` · `DELETE /tests/:id` · `POST /tests/:id/like` · `POST /tests/:id/report` · `GET /me/tests` · `GET /tests/:id/stats`.

Для personality-тестов веса не отдаём клиенту (чтобы нельзя было «подсмотреть»), результат считает сервер.

## 5. Вирусность при ограничениях платформы

`share()` ведёт только на страницу игры. Что делаем:
- Результат сразу показывает «Ты — Наруто (23% прошли так же)» — красиво, хочется показать, но…
- **Идея-обход**: после шаринга друг открывает игру и видит на главной блок «Тест, который прошли недавно» / «Популярное сегодня» — шанс попасть в тот же тест. Плюс код теста (короткий, напр. `NR7K`) на странице результата и поле «Ввести код теста» на главной — друзья могут обменяться кодом текстом.
- Профиль автора через `openProfile` — для подписчиков автора.
- Уточнить у админов huEVO, можно ли будет передавать custom query в share (стоит спросить — это сильно усилит рост).

## 6. Этапы

**MVP (1–2 недели)**
1. Репозиторий, Vite+TS, backend, БД, деплой на домен.
2. Регистрация игры в huEVO (draft, режим test), `huevo.init()` + `/login` с проверкой hash.
3. Каталог + прохождение + результат для personality-тестов (пока 3–5 тестов, засеянных вручную: Наруто, Гарри Поттер, и т.п.).
4. Конструктор personality-теста с предпросмотром и публикацией.
5. Лимиты, жалобы, ручной скрыть/удалить.
6. Подать на модерацию huEVO.

**Этап 2**
- Quiz-тип, лайки, статистика автора, поиск/теги, код теста.
- Загрузка обложек (с premod), топы недели.

**Этап 3**
- Монетизация (по желанию): платные «премиум»-оформления результата через payments API, выплаты авторам популярных тестов через credits API.

## 7. Риски

- Нет deep-link в share → медленный органический рост (см. п.5).
- Спам/неприемлемый контент → жалобы, автоскрытие, лимиты, бан.
- Редирект на другой origin ломает SDK (`timeout`) → фронт отдаём ровно с домена из настроек.
- Нужен собственный хостинг и домен (платформа ничего не хостит).

## 8. Решения (приняты)

- Хостинг: **Cloudflare** (Workers + D1 + Static Assets; фронт и API на одном origin).
- Фронт: **Preact + Vite + TS**.
- Викторина (quiz) — **в MVP**, вместе с «кто ты».
- Картинки результатов: готовый набор (эмодзи + градиенты), загрузка — позже.

## 9. «Репост себе на страничку» — что реально можно

В SDK **нет** метода, который публикует что-то на стену/страницу пользователя. Есть только `huevo.share()`: системное меню «Поделиться» (Web Share) или копирование ссылки в буфер, и ведёт оно на страницу игры, а не на тест.

Что делаем в MVP:
- На экране результата кнопка **«Поделиться»** → `huevo.share()`.
- Рядом **код теста** (напр. `NR7K`) и крупная красивая карточка результата — её можно скриншотнуть и выложить на свою страничку руками.
- Друг вводит код на главной и попадает в нужный тест.

Что спросить у админов huEVO: (а) можно ли будет в `share()` передавать текст/параметры; (б) будет ли метод публикации на стену. Если появится — подключим одной кнопкой.

## 10. Донат автору теста (необязательный, монетками)

Платёж идёт от игрока в кошелёк игры, а выплата автору — через `POST /credits` (выплаты не требуют подтверждения, автор должен быть «игроком», то есть открывал опубликованную игру — создатель теста им по определению является).

**Флоу:**
1. На результате/странице теста кнопка «Поддержать автора» → выбор суммы (5 / 10 / 50 / своя, 1–100 000).
2. Frontend → `POST /donate {test_id, amount}`; сервер создаёт `POST /payments` (`user_id` донатера, `description` «Донат автору … за тест …», `idempotency_key` = id заказа из нашей БД, `test` = режим запуска).
3. Frontend → `huevo.confirmPayment(intent_id)` (результат фронта не доверяем).
4. Сервер узнаёт итог через **коллбек** (`POST /callback/payment`, проверка `X-Huevo-Signature` = HMAC(SHA256(secret), сырое тело)) и/или `GET /payments/{id}` как запасной вариант.
5. При `succeeded` — **один раз на `intent_id`** — `POST /credits` автору: сумма минус комиссия игры (напр. 10%; решить), `idempotency_key = donate-{intent_id}`, `reason` «Донат за тест».
6. Записываем в `donations(id, intent_id, from_user, to_user, test_id, amount, payout, status)`; автор видит сумму донатов в «Моих тестах».

Нюансы:
- В режиме `test` монеты не двигаются — идеально для отладки, пока игра не опубликована.
- Если у автора `not_a_player`/`player_restricted`/`limit_exceeded` — статус `payout_pending`, повторяем выплату кроном.
- Нельзя донатить самому себе; антиспам: лимит донатов в минуту.
- Коллбек: только `https`, порт 443, адрес указать во вкладке «API» настроек приложения.
